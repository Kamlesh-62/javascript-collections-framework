Add `TreeMap`, a map kept in the order of its keys and stored as a balanced binary search tree, with the `SortedMap` and `ReadonlySortedMap` types, the `TreeMapOptions` type and the `isSortedMap` guard. It has the whole map API (`get`, `set`, `has`, `delete`, `getOrInsert`, `getOrInsertComputed`, `compute`, `merge`, `replaceAll`, live `keySet()`, `entrySet()` and `valueCollection()` views), with iteration and output in key order. `get`, `set`, `has`, `delete` and the nearest-entry queries `lowerEntry`, `floorEntry`, `ceilingEntry` and `higherEntry` are O(log n); `firstEntry`, `lastEntry`, `pollFirstEntry` and `pollLastEntry` reach the ends. Entries are live handles on (map, key). Questions about keys alone go through `keySet()`, a live sorted set. `subMap`, `headMap` and `tailMap` (with the `SubSetOptions` and `BoundOptions` inclusive flags) return live range views, and `reversed()` a live descending view. It orders by natural order or by the `comparator` option, and the comparator decides key sameness. Like a native `Map`, `set` returns the map, lookups of `null` or of keys of another kind answer absent in natural order, and `-0` is stored as `0`. A comparator that throws or returns `NaN` leaves the map unchanged (`putAll` keeps the mappings it set before the failure); iteration fails fast; `equals` compares mappings, so a `TreeMap` equals a `HashMap` with the same mappings. Building from keys in ascending order takes O(n). The documentation of `SubSetOptions`, `BoundOptions` and `MapEntry` now covers sorted maps (no type change).
